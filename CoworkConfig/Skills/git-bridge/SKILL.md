## 1. How this actually works (read this first)

There is no git MCP server. An earlier version of this skill described tools on port
8934 (`git_status`, `git_diff_unstaged`, `git_log`) that were never installed — calling
them fails. Git needs no server of its own: it is a command-line program, and the
command bridge already runs command-line programs on this machine under Jordan's
approval flow.

| Item | Value |
|---|---|
| MCP server used | Jordan Approved Batch Executor 8933 |
| Namespace | jordan-approved-batch-8933-v1 |
| Tool | `run_batch_file` (relative path to an existing .bat under CommandJobs) |
| Repository root | C:\Users\YOURUSER\Documents\COPILOT_COWORK |
| Remote | NONE — this repository is local only and must never gain one |

The repository covers the whole Cowork working folder: `Startup\` (bridge configuration),
`CommandJobs\` (job scripts), `Outputs\` (deliverables), and anything else Jordan keeps
there.

**The mechanic for every operation in this skill is the same three steps:**

1. Author a .bat file containing the exact git commands.
2. Write it to `CommandJobs\` with the filesystem bridge (`jordan-local-filesystem-8932-v1`
   `write_file`).
3. Call `run_batch_file` with its relative path, then report stdout, stderr and exit code.

Under Jordan's approved 8933 workflow, a read-only job (status, diff, log, show) is
proposed, approved once, written, and run immediately. A job that commits, reverts, or
otherwise changes state must show the exact commit message and file list in the proposal
before it is written.

### Batch authoring rules that apply here

- **CRLF.** Files written through the 8932 bridge arrive LF-only, and cmd mis-parses
  LF-only .bat files — sometimes with a silent early exit rather than an error. After
  writing any job, run `CommandJobs\2026-08-18-fix-crlf-all.bat` before running the job
  itself.
- Start every job with `cd /d C:\Users\YOURUSER\Documents\COPILOT_COWORK`. The 8933
  environment is stripped and the working directory is not inherited.
- Add `--no-pager` to any git command that could page (`git --no-pager log`,
  `git --no-pager diff`). A pager will hang the job.
- Echo a delimiter before each command (`echo ===STATUS===`) so multiple commands in one
  job can be told apart in stdout.
- Prefer one job per logical operation. Do not build a menu-driven .bat with `call :label`
  — label handling is the exact construct LF endings break.

## 2. Repository initialization

`git init` was approved but the repo may not exist yet — verify before assuming. A job
that runs `git status` in a folder with no `.git` returns a fatal error, which is the
check.

The init job must, in this order: `git init`, write `.gitignore` (contents in section 6),
`git add` the named files, and make the first commit. Do not `git add .` even on the
first commit — `Outputs\` may contain very large binaries.

## 3. Why this exists

Before version control, the only rollback was a hand-written backup file — `tasks.json`
has `.pre-8933-stateful-backup` and `.pre-8932-stateful-backup` siblings precisely because
there was no history. Every configuration change was a one-way door guarded by remembering
to copy a file first.

With history available, that discipline is replaced by something reliable: commit before a
change, commit after, and any mistake is one `git revert` away.

**What git does not cover.** The repository tracks files only. It does not capture system
state — installs, scheduled tasks, registry entries, firewall and port visibility — which
is where the worst incidents on this machine have originated. Do not describe a git commit
as a full rollback point. Memory carries the judgment; git carries the facts.

## 4. When to use it (proactively, not only on request)

- **Before editing** anything under `Startup\` — bridge configuration is the highest-risk
  surface on the machine. A broken `tasks.json` costs every bridge at once.
- **After completing** any batch of edits, so the change is captured while its rationale is fresh.
- **When Jordan asks what changed** — `git diff` is authoritative where memory and chat history
  are not.
- **When something breaks** — `git log` and `git diff` identify what moved, instead of guessing.

## 5. Workflow

1. **Read first.** Run a status/diff job before proposing anything. Never describe a change
   without reading the actual diff.
2. **Summarize in business language.** Report what changed and why it matters, not raw hunks,
   unless Jordan asks for the diff itself.
3. **Propose the commit.** Show the exact files to be staged and the exact commit message,
   then let the approval card be the gate. Never stage `.` blindly — name the files.
4. **Commit message format:** a short imperative subject line, then a body explaining WHY.
   Reference the conversation's decision, not the mechanics.

   ```
   Add --stateful to the 8932 filesystem bridge

   8932 dropped three times in one session while running stateless.
   Matches the fix already applied to 8931 and 8933. KnownGood updated
   so bridge-restore-tasksjson.bat will not revert it.
   ```

   In a .bat, pass the message as repeated `-m` flags — `git commit -m "subject" -m "body"`
   — rather than trying to embed newlines.
5. **Verify.** Run `git --no-pager log -1` after committing and report the real commit id
   from stdout. A zero exit code alone is not confirmation.

### Worked example — the status job

```bat
@echo off
cd /d C:\Users\YOURUSER\Documents\COPILOT_COWORK
echo ===STATUS===
git status --short
echo ===DIFF===
git --no-pager diff --stat
echo ===LOG===
git --no-pager log -5 --oneline
exit /b %ERRORLEVEL%
```

## 6. Reverting

When Jordan asks to undo something: identify the commit with `git --no-pager log`, show him
what that commit contains with `git --no-pager show <sha>`, and propose `git revert --no-edit <sha>`
— which creates a NEW commit undoing the change. Never `reset --hard`. Revert preserves
history; reset destroys it, and a destroyed local history has no remote to restore it from.

## 7. What must never enter the repository

Large binaries poison a git history permanently — once committed, removing them requires
rewriting every subsequent commit. `.gitignore` must exclude at minimum:

```
Outputs/**/*.exe
Outputs/**/*.gguf
CommandJobs/Logs/
**/_job-state.txt
```

Before any `git add`, check for files over ~10 MB and refuse to stage them; say plainly that
the file is too large for version control and belongs in the output folder only. The 1.46 GB
`OllamaSetup.exe` is the concrete example of what this rule exists to prevent.

## Guardrails

- **Never call a port-8934 tool.** That server does not exist. If a future session installs a
  real git bridge, this skill must be rewritten deliberately, not assumed.
- **Never run a destructive git command.** `reset --hard`, `clean -fd`, `checkout --force`,
  `branch -D`, `rebase`, `commit --amend` on an existing commit, and any history rewrite are all
  prohibited. Every one of them can discard work that has no remote backup.
- **Never add a remote and never push.** No `git remote add`, no `git push`, no `git clone` into
  this repository. Firm data must not leave the machine through a git remote — this is the single
  most important rule in this skill.
- **Always read the diff before describing a change.** Do not summarize from conversation memory;
  memory drifts and the working tree is the truth.
- **Never stage blindly.** Name each file, so an unnoticed file cannot ride along into a
  commit. ONE deliberate exception (2026-08-24): the standing `cowork-close.bat` runs
  `git add -A` only after printing the complete working tree and diff stat earlier in the
  same job. That review IS the protection — nothing rides along unseen, because the full
  tree was displayed and shown to Jordan before he approved. Outside that
  reviewed-then-staged pattern, `git add .` and `git add -A` stay prohibited.
- **Never let a job commit its own ephemeral inputs.** A commit job's message file or scratch
  input must be gitignored AND untracked (`git rm --cached`), or `git add -A` sweeps it into
  the commit and the job's own cleanup then leaves a tracked-but-missing file behind. Note
  that `.gitignore` alone cannot fix this once the file is tracked — gitignore applies only
  to untracked files.
- **Never commit secrets.** Before staging, scan the diff for tokens, passwords, connection
  strings and API keys. If one is present, refuse to stage that file and tell Jordan which line.
  A committed secret persists in history even after deletion.
- **Never commit a file over ~10 MB** — confirm with Jordan first, and prefer excluding it.
- **Always show the exact commit message and file list before committing.**
- **Do not resolve a merge conflict silently.** Report the conflicting files and ask.
- **Report the real command output.** Never claim a commit succeeded without confirming the
  commit id, and never summarize away an error. If a job returns a non-zero exit code, report it
  rather than retrying blindly.

## Output format

For a status or change request:

- **What changed** — plain-language summary, grouped by area (bridges, jobs, skills, outputs)
- **Files** — each path with a one-line description of the change
- **Risk** — anything that affects bridge startup or job execution, called out explicitly
- **Proposed commit** — the exact message, and the exact list of files to stage
