## Honest scope — read this before trusting it

This is **not** a runtime learning loop. It changes no model, no weights, and no
platform behavior. It is an instruction that a session chooses to follow, in the
same way the persistent-memory directive is — that directive was observed firing
unprompted on 2026-08-18, which is evidence it works, not a guarantee.

It observes **only what happens inside a Cowork session**. A job that fails on the
PC when no session is watching is invisible to it.

Its power is entirely in being **read before acting**, and that is exactly the part
that has been measured and found unreliable.

**Measured 2026-08-28.** The pre-task scan below is written into
`copilot-instructions.md`, which loads unconditionally every session. It was still
skipped: a bridge was declared unavailable for a whole session while 17 bridge keys
sat in this file, two of them at 2 hits describing that precise failure. The same
failure had already occurred on 2026-08-24 and 2026-08-25. Three sessions, one
unconditional rule, three misses.

Draw the right conclusion. A preamble is skippable in silence, and prose has the worst
compliance record in this whole project. So this skill no longer rests on the scan
alone. The scan is the cheap first pass; **the closing check below is the part that can
actually fail**, and it is the reason the skill is worth loading.

## THE OPENING LOOKUP — how a lesson reaches you before you need it

The pre-task scan below failed three times because it asks for an action: open a
115 KB file. Two things now carry that load instead, and only the first needs nothing
from you.

**1. The digest, which loads whether or not you remember it.** The highest-value rules
live as one-liners inside `copilot-instructions.md`, between the `LESSON-DIGEST`
markers, because that file loads unconditionally every session. A rule there is already
in context before the first tool call. This is the only delivery path measured to work.
Regenerate it after adding a rule or changing a Hits count:

```bash
python scripts/digest_apply.py \
  --lessons <path>/cowork-lessons.md \
  --instructions <path>/copilot-instructions.md
```

`digest_apply.py` regenerates AND splices in one step. Use it instead of pasting the
block by hand: the hand-splice is the reason a digest drifts, because detection was
automated and the fix was not. It prints `already current` or `applied: N rules from M
entries`, writes a `.pre-digest.bak` first, and REFUSES to write unless everything
outside the markers is byte-identical and the new block re-extracts from DISK after
writing - so a partial write cannot report success. `--check` reports staleness and exits
1 without touching anything, which makes it usable as a gate on its own.

`lesson_brief.py --digest` still prints the block if you want to inspect it. Do not pass
`--limit` when regenerating the real block: it caps the output and drops the
lowest-ranked rules, which are the newest ones. It warns on stderr when it truncates, but
the block it prints still looks complete and its trailing count still agrees with itself
- a regeneration that SHRINKS the block is the signature of
`lessons-digest-default-limit-truncates`. `digest_apply.py` removes the need to eyeball
that, since it compares against a fresh full regeneration every time.

**2. One-call detail, when a rule applies and you need the mechanism:**

```bash
python scripts/lesson_brief.py <path>/cowork-lessons.md --for bridge
```

Surfaces are `bridge`, `files`, `memory`, `skills`, `git`, `claims`. Sub-second, returns
only the matching rules. **Run this before the first tool call on any surface you are
about to touch.** It is one call and it removes the cost excuse the old scan created.

**3. The gate, which FAILS instead of advising.** `lesson_brief.py --for <surface>` is a
lookup you may or may not perform; prose that asks for an action does not reliably get the
action, which is the finding this whole skill rests on. `lesson_gate.py preflight` prints
the same rules and additionally fails on a stale digest or an unruled repeat offender, and
writes a receipt that `lesson_gate.py verify` checks before a state-changing step:

```bash
python scripts/lesson_gate.py preflight --surface bridge \
  --lessons <path>/cowork-lessons.md --instructions <path>/copilot-instructions.md \
  --session <id> --receipt-dir <path>/.lesson-receipts

python scripts/lesson_gate.py verify --surface bridge \
  --instructions <path>/copilot-instructions.md \
  --session <id> --receipt-dir <path>/.lesson-receipts
```

`audit` is the non-gating inventory: which surfaces are clean and which carry a repeat
offender that cannot reach the digest. `lesson_gate_selftest.py` breaks every gate
deliberately and asserts each one fires - 28 cases, including negative controls proving a
clean surface is not punished for another surface's gap, and one proving an unwritable
receipt directory exits 2 rather than 1. That case is itself negative-controlled: run
against the pre-fix script it is the ONLY assertion that fails, at rc=1.

`--receipt-dir` must point somewhere WRITABLE. Omit it and it resolves through
`default_receipt_dir()` - `COWORK_RECEIPT_DIR`, else `.lesson-receipts` under the current
directory, else a temp directory - and preflight and verify both call that one function, so
they cannot resolve differently. The exit codes are three-valued on purpose: 0 clean,
1 a rule failure you must fix, **2 the gate could not RUN** - every rule loaded and passed
but the receipt could not be written. A read-only mount is an exit 2, never an exit 1;
reading it as a rule failure would halt a close over an environment fault
(`lessons-gate-receipt-dir-read-only`, measured 2026-09-01).

### The `Rule:` field

A digest line comes from an authored `- **Rule:** ...` field on an entry, never from an
auto-summary of the Worked line. A script cannot compress a paragraph into an imperative
without inventing, and an invented rule is worse than none. Write it as one imperative
sentence a future session can act on without opening the entry.

`lesson_check.py` FAILS any entry at Hits >= 2 with no `Rule:` field, because a repeat
lesson with no digest line depends on somebody opening the archive, which is the exact
dependency that failed. Find them with `--missing-rules`.

## Contradiction handling — the part that matters most

Wrong memories cost more than missing ones: a session acts on them confidently.

1. **Correct the source first** — edit the wrong memory file, memory entry, or lessons
   entry. Never leave true and false versions coexisting.
2. **Then log** a `contradiction` entry naming the corrected item.
3. **Say so in chat**, plainly: "correcting what I had on file." Jordan may still be
   carrying the wrong version in his head; a silent file edit does not reach him.

**When the wrong belief IS an entry in this file** (self-contradiction), steps 1 and 2
collapse into a single in-place edit of that entry: keep its `Pattern-Key`, set
`Trigger: contradiction`, rewrite `Failed`/`Why`/`Worked`, bump the date, and move it
to the Contradictions section. Do **not** create a second entry — that would duplicate
the key and break dedupe. If the *method* that produced the wrong belief is itself
reusable, that — and only that — earns a new key, cross-referenced both ways.

**Memory store vs. file.** If the wrong belief is also held as a saved memory entry
(not just in this file), correct **both**. The saved entry is what loads automatically;
fixing only the file leaves the confident wrong version in play.

## Capture triggers

An event must pass **the gate** above *and* match a row here.

| Trigger | Fires when | Record |
|---------|-----------|--------|
| `failure` | A tool, bridge call, or batch job fails **and the fix was non-obvious, or the same failure could plausibly recur** | The exact call/arguments, the error, what succeeded instead |
| `correction` | Jordan corrects **a belief you acted on** — not a standing preference | What you believed, what is true, how the belief formed |
| `contradiction` | Evidence disproves something already stored | The wrong entry's key, the evidence, the correction |
| `false-success` | A verification step reveals a reported success was false | What claimed success, how the check caught it |
| `better-approach` | A materially better method is found for something **recurring** | The old way, the new way, why the new one wins |
| `missing-capability` | A capability is requested that does not exist | What was wanted, the closest available path |

**Multi-trigger precedence.** When an event matches several rows, use the FIRST match
in this order: `contradiction` > `false-success` > `correction` > `failure` >
`better-approach` > `missing-capability`. Rationale: the rarer, higher-harm class wins,
so the section an entry lands in stays predictable across sessions.

**Standing preferences are not corrections.** "Actually, always use my work address"
is a policy about how Jordan wants things done — it goes to persistent-memory. A
correction is about a *belief you acted on being wrong*. The word "actually" is not
the test; the substance is.

## Two phases, two contexts — observe during, analyse after

A model executing a primary task does not have the spare attention to analyse its own
workflow at the same time. Reflection folded into the working context is the reason this
routine has silently failed to fire before. So the loop is **split**, and the split is the
architecture — not a style preference.

### Phase 1 — OBSERVE (primary agent, during the work, cheap)

While working, append raw observations to `working/.reflect-log.md`. This is
**stenography, not judgment**: no gate, no trigger classification, no Pattern-Key, no
prose. If it takes more than one line, it belongs in Phase 2.

- **Append at every phase boundary and at every failure** — a job finishes, a file is
  published, a diagnosis is confirmed, a call errors. Capture the moment it happens.
- Record the **perishable** facts only: the exact call and arguments, the verbatim error
  text, the exit code, what was tried next, whether it worked. These are gone by the
  summary; the reasoning about them is not.
- **Never skip because it seems minor.** A one-call failure with a non-obvious fix is
  exactly as loggable as a long one — this loop reliably under-fires on short work.
- If nothing notable happened, write nothing. An empty log is a valid result.

```
[2026-08-24T14:02Z] bridge call failed
call: run_batch_file bridge-health.bat
err:  "connection lapsed" — exit 1
next: re-called same args in a new turn -> exit 0, no restart
```

### Phase 2 — REFLECT (separate agent, fresh context, after the work)

When the primary task **finishes**, dispatch a sub-agent whose entire context is the
observation log plus this skill. It does the analysis the working agent could not.

Dispatch it with a brief that says exactly this:

> Read `working/.reflect-log.md` and `<this SKILL.md>`. For each observation, apply THE
> GATE. For those that pass, classify by trigger, assign or match a `Pattern-Key`, and
> write the entries to the lessons file in the prescribed format. Handle contradictions
> by correcting the source entry first. Report what you logged and what you rejected,
> with the reason for each rejection. Do not fix code, do not continue the primary task,
> and do not log anything the log does not support.

**Why a separate agent, not a final step in this one:** a fresh context cannot rationalise
the work it just did. The working agent knows why each choice felt right at the time, and
that is precisely the bias that makes it a poor judge of its own trajectory.

**The dispatch is not optional and not conditional on the log looking interesting.** If
observations exist, the reflector runs. Judging the log's worth before dispatch re-imports
the bias the split exists to remove.

**When a sub-agent is unavailable**, do Phase 2 inline — but do it *after* declaring the
primary task complete, from the log alone, and say in chat that reflection ran in-context
rather than isolated. A stated degradation is fine; a silent one is not.

### What each phase may NOT do

| Phase | May not |
|-------|---------|
| OBSERVE | Apply the gate · classify triggers · assign Pattern-Keys · write to the lessons file · draw conclusions |
| REFLECT | Continue the primary task · fix code · edit anything but memory/lesson files · invent an observation the log does not contain |

## Sections and where entries go

The lessons file has exactly three sections. Trigger determines section:

| Section | Holds | Triggers |
|---------|-------|----------|
| `## Failures` | Traps with a known fix | `failure`, `correction`, `false-success`, `better-approach`, `missing-capability` |
| `## Contradictions — stored memories that proved wrong` | Beliefs that were stored and were wrong | `contradiction` |
| `## Open questions` | Known-unresolved issues, no fix yet | any trigger, when `Worked` is genuinely unknown |

**Insert into the SECTION, never at the end of the file.** This is the one that actually
goes wrong. `## Failures` is the FIRST section, so an entry appended "at the end" lands
under `## Contradictions` or `## Open questions` instead - silently, because nothing
checks. An audit on 2026-08-28 found **21 of 65 entries misfiled** this way, every one of
them a recent append. Anchor the insert on the heading that FOLLOWS your target section
(insert a `failure` entry immediately before the `## Contradictions` heading), and after
writing, confirm your new entry sits above that heading. Two trigger values had also
drifted out of the table below (`better-method`, `false-failure`); both were remapped.

**Open-questions lifecycle.** An entry sits here only while unresolved. When it is
solved, **move** it (do not copy) to the section its final trigger dictates, rewrite
`Worked` with the actual fix, bump the date, and delete the stale "still open" text.
Never leave a solved item advertised as open.

## Promotion — a lesson that recurs must stop being a lesson

The lessons file is a **staging area**, not the final home of a rule. A trap that keeps
biting is evidence the rule is in the wrong place: it is being read only by whoever
happens to scan the file, when it should be loading unconditionally.

**Promote when either condition holds:**

1. The entry's `Hits` counter reaches **2** — the second hit is the signal. Increment `Hits`
   on the existing entry, never open a second one, and propose promotion in that same pass
   rather than waiting for a third hit, or
2. A single `measured` lesson changes a **standing rule** — what is allowed, what is
   forbidden, or which surface owns a job.

**Promotion targets — pick the narrowest one that always loads:**

| Target | Use for | Example |
|---|---|---|
| `Documents/Cowork/copilot-instructions.md` | Behaviour that must hold no matter which skill is driving | "there is no fallback when 8933 is down" |
| The owning `SKILL.md` | A procedure or trap specific to one subsystem | the CRLF normalizer step before running a job |
| A memory file in `cowork-memory/` | Durable topic context, not a rule | measured drop rates, folder layout |
| **A new skill** | A whole repeatable procedure, not a single rule | a fixed multi-step routine run often enough to name |

**Rules for promotion:**

- **Promote, then point.** Add `- **Promoted-to:** <file / section>` to the lesson entry.
  The entry stays as the evidence trail; the rule now lives where it loads.
- **Fix every surface that states the rule, not just the one that prompted the change.**
  Grep the instructions file, every `SKILL.md`, the memory folder, and stored memories for
  the old wording. A rule is settled only when the surfaces agree — see Pattern-Key
  `config-contradiction-survives-in-second-file`.
- **Never promote a `reported` lesson.** Promotion needs `measured` evidence; an inference
  hardened into a standing rule is how a wrong belief becomes permanent.
- **Never write a new skill unprompted.** Propose it to Jordan with what it would do and
  what it replaces, and let him decide. Autonomously generated skills are exactly the
  artefacts that look right and fail on first real use.

**Capability gaps go to a build list, not the failures log.** A `missing-capability`
entry describes something that does not exist yet; it is a feature request, not a trap.
Keep it short, name the closest available path, and surface it in the session summary so
it can be built or dropped, rather than accumulating as pseudo-failures.

## Entry format

```
### <short imperative title>
- **Pattern-Key:** <subsystem>-<short-behavior>
- **Supersedes key:** <old-key>   (only if this entry was ever renamed)
- **Date:** YYYY-MM-DD
- **Trigger:** failure | correction | contradiction | false-success | better-approach | missing-capability
- **Failed:** <what was tried, concretely — exact args/commands, credentials redacted>
- **Why:** <mechanism, one or two lines — not speculation>
- **Worked:** <the approach that succeeded>
- **Evidence:** measured | reported   (+ "inference unverified" if the Why is reasoning, not observation)
- **Hits:** <integer>   (how many separate sessions have hit this trap — starts at 1)
- **See also:** <other Pattern-Key>   (optional — omit if none)
- **Promoted-to:** <file / section>   (only once promoted — see Promotion)
```

**`Hits` is the promotion counter — increment it, never open a second entry.** When a trap
is hit again, find the entry that owns the Pattern-Key, add 1 to `Hits`, bump `Date`, and
widen `Failed` / `Worked` if the new occurrence taught something the old wording missed. A
second hit is not a new lesson; it is proof the existing lesson was not read early enough,
which is exactly what promotion fixes. An entry with no `Hits` line predates the field —
treat it as `Hits: 1` and add the line the next time you touch it. Never reset a counter to
make an entry look settled.

### Pattern-Key naming — this is what makes dedupe work

Format: **`<subsystem>-<short-behavior>`**, kebab-case, subsystem FIRST. Dedupe fails
silently if two sessions name the same trap differently, so the subsystem prefix is
mandatory and drawn from this fixed list:

`bridge` (any/all bridges) · `bridge-8931` · `bridge-8932` · `bridge-8933` · `batch` ·
`git` · `schtask` · `onedrive` · `graph` · `teams` · `outlook` · `excel` · `memory` ·
`skill` · `watchdog`

If nothing fits, use the tool or subsystem's own name — never a bare description.
**Before writing, scan the existing keys for the same prefix.** If a related entry
exists, update it rather than adding a sibling.

**Never rename a key silently.** The key is the only retrieval mechanism — there is no
fuzzy match and no title search, so a rename breaks every lookup held by an older
session, saved memory, or `See also` line. If a key must change, keep the entry and add
`- **Supersedes key:** <old-key>` so the old name still finds it.

### Two rules that keep the file trustworthy

1. **Update, do not append, on a repeat.** Same `Pattern-Key` → edit in place: sharpen
   the mechanism, bump the date. Three near-duplicates for one trap is worse than one
   crisp entry.
2. **Tag the outcome, not the explanation.** `Evidence` describes the `Failed`/`Worked`
   lines — what was actually observed. If the `Why` is your reasoning rather than
   something you probed, append **"inference unverified"**. A sound measurement with a
   wrong inference drawn from it is a real failure mode: it is how a `measured` entry
   ends up wrong. **A bare `measured` means the tag was considered and the Why was
   observed — not that nobody looked.** When you touch an entry, audit its tag.

3. **Never quote a figure that decays.** Do not record file sizes, line counts, or
   timestamps as the proof of a check — they go stale and hand a later session a false
   negative when it compares against them. Record what was checked and how, not the
   reading.

### Redaction

Replace any token, key, password, or credential with `<redacted>` — including inside
a `Failed` line that otherwise reproduces exact arguments. Never record the value.
This overrides "exact args/commands".

## Maintenance

Run `scripts/lesson_check.py` first. It answers most maintenance questions
mechanically and will not miss what an eye-scan of 115 KB misses.


- Before appending, scan existing keys sharing the subsystem prefix.
- **Audit the file periodically — stored lessons are not automatically right.** A lesson
  drawn from one incident can encode a coincidence as a rule. On any audit pass, or
  whenever an entry is relied on and turns out unhelpful: re-read its `Evidence` line,
  downgrade or delete anything `reported` that never got confirmed, and delete outright
  any entry whose `Worked` line has been overtaken. A wrong lesson is worse than no
  lesson, because it is followed with confidence.
- **A promoted lesson is a pruning candidate.** Once a rule loads unconditionally from
  instructions or a SKILL.md, the entry's job is historical evidence only — keep it short
  or retire it.
- Prune entries older than six months whose `Worked` line has become default behavior,
  or whose subsystem no longer exists.
- The file should stay scannable. If a section exceeds roughly forty entries, the
  problem is under-pruning, not a need for a bigger file.

## Failure handling — when the routine itself fails

Self-improvement is the first thing to break quietly, because nothing downstream depends
on it. Handle these explicitly rather than skipping the step:

| Situation | Do this |
|---|---|
| The lessons file cannot be read (mount, bridge or OneDrive unavailable) | Say plainly that the scan did not happen — never let silence imply a clean scan — proceed with the task, and capture the session's lessons into the reply so Jordan can paste them if the file stays unreachable |
| A write to the lessons file fails or is denied | Report it; do not claim the lesson was logged. An unlogged lesson stated in chat beats a fabricated confirmation |
| Two entries give conflicting guidance | Follow the one with `measured` evidence and the later date, then reconcile them in the same session — a contradiction left standing will be followed at random next time |
| An entry's `Worked` line no longer works | That is a `contradiction`: rewrite the entry in place, add `Supersedes key`, and say the old guidance was wrong. Never leave both versions readable |
| The task is failing and a lesson is being written about it | Finish the fix first. **Logging is not fixing** — a lesson entry is never closure for a broken deliverable, and must not be offered as one |
| Nothing worth logging happened | Say "nothing new to log". An empty log is a valid result; a skipped scan is not, and the two must never be reported the same way |

## When NOT to Use

- **Durable topic context or a standing preference** ("always use my work address") →
  `persistent-memory`, even when it arrives phrased as a correction.
- **A one-off fact, a raw transcript, or a passing observation** — nothing recurs, nothing
  to log.
- **Transient noise that resolved itself** — a retried call that then worked is not a lesson
  unless the retry discipline itself was the lesson.
- **Judging how a person performed.** Log what a *system* did, never what someone is like.
- **Fixing the current failure.** Diagnose and repair first; this skill records the outcome,
  it does not substitute for it.
- **Storing secrets** of any kind, in an entry or a commit message.

## What NOT to log

- Secrets, credentials, tokens, one-time codes
- Client-confidential detail beyond the minimum needed to state the lesson
- Judgments about people's performance or competence
- Transient noise with no reusable rule ("the network blipped")
- Standing preferences and durable topic context — those belong in persistent-memory


## Guardrails

- **Never fabricate an entry.** Every `Failed`, `Worked` and `Evidence` line must describe
  something that actually happened this session, with the real arguments, error text and
  exit code. If the detail was not captured, say so in the entry rather than reconstructing
  it — an invented lesson is followed with the same confidence as a real one. "Nothing new
  to log" is always available and always preferable.
- **Mark evidence honestly.** `measured` means a check whose output was read; `reported`
  means a tool claimed success and nothing confirmed it. Never upgrade one to the other to
  make an entry look stronger, and never promote a `reported` lesson into a standing rule.
- **Editing the lessons file is destructive — rewrite in place, never wholesale.** Update
  the entry that owns the Pattern-Key. Never rewrite, reorder or truncate the file as a
  whole, never delete an entry to resolve a disagreement with it (supersede it and say the
  old guidance was wrong), and never overwrite the file from memory of its contents — read
  it first. Prior versions exist as `.bak` siblings and in git; do not rely on that as a
  licence to be careless.
- **Never edit a file Jordan did not ask you to change** to make a lesson true. Report the
  discrepancy instead.
- **Promotion is a proposal, not a licence.** Changing `copilot-instructions.md`, another
  skill, or creating a new skill is shown to Jordan first, with the exact wording.
- **When data is missing, stop and say so** — an unreadable lessons file, a denied write, or
  an entry whose facts you cannot reconstruct are all reported plainly. Never let silence
  imply the scan ran clean.
- **No secrets, no client-confidential detail, no performance judgments** — in entries,
  summaries, or commit messages.

## Relationship to the other skills

| Skill | Owns |
|-------|------|
| `persistent-memory` | Durable topic context, standing preferences, judgment — the narrative |
| `self-improvement` | Behavioral corrections — what not to do, and what to do instead |
| `git-bridge` | File-level history of `COPILOT_COWORK` — the facts |

Memory carries the judgment, git carries the facts, lessons carry the scar tissue.
Git does not capture system state (installs, scheduled tasks, registry, port
visibility) — exactly where the worst incidents came from, and exactly why the lessons
file must carry those in prose.

## Where these practices come from

Reviewed 2026-08-21 against two published self-improving-agent designs. Both are external
sources, not firm guidance; what was adopted and what was rejected:

- **Hermes self-improvement loop (GEPA)** — agentwikis.com/wiki/hermes/wiki/concepts/self-improvement-loop.md.
  A five-stage loop — trajectory capture, periodic review, skill packaging, persistent
  memory, compounding reuse — whose review fires on a **tool-call cadence** (default ~15)
  rather than only at session end. *Adopted:* mid-work capture — but as raw OBSERVATION
  only (Phase 1); the analysis it folds into the working context is deferred to an isolated
  Reflector (Phase 2), because in-context reflection is why this routine silently failed to
  fire on 2026-08-21. *Rejected:* autonomous self-editing of prompts and unprompted skill
  creation. That page rates its
  own confidence as medium and warns that generated skills are frequently wrong on first
  run, which is why promotion here proposes rather than writes.
- **OpenClaw self-improvement / self-improving-agent** — github.com/YMIR777/openclaw-memory
  and docs.bswen.com/blog/2026-03-27-self-improving-agent-openclaw. Separates learnings,
  errors and feature requests into distinct logs, and **promotes** recurring patterns out
  of the log into standing rule files. *Adopted:* the promotion ladder, capability gaps as
  a build list rather than failures, periodic review of stored lessons (its author reports
  the log learning the wrong thing from a coincidence), and its stated limit that
  *logging is not fixing*.
