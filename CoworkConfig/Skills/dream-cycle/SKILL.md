## What this is

The lessons log and the memory files only ever grow. Nothing merges two entries
that describe the same failure, retires a claim a later entry disproved, or asks
whether a finding can reach a session at all. This routine does that sweep on a
schedule, the way sleep consolidates a day rather than recording it again.

It runs in two halves, deliberately:

- **Mechanical** - `dream_analyze.py` counts what can be counted: reachability
  per surface, near-duplicate pairs, shouted retirement markers, still-open
  items, relative-date anchors, index/file agreement, digest growth.
  Deterministic, self-tested, read-only.
- **Judged** - the agent reads those findings plus the day's commits and writes
  a proposal. Judgement is where fabrication lives, so it is fenced (below).

**`references/determinism.md`** holds the exact shapes - corpus checkpoint,
fingerprint canonicalisation, State/Outcome validity matrix, run-evidence block,
rerun naming, the analyser release gate, and the report-write-failure path. Load
it when writing a report, computing a fingerprint, or deciding a no-op. It lives
separately because this file is read in full every time the skill activates, and
a specification nobody needs mid-analysis should not be competing for that
context.

Every file this skill reads is declared here. `manifest_check.py` FAILS if the
skill references a dependency that appears in neither list, which is the defect
that shipped three times on 2026-08-30 - `lesson_gate.py`, `analyser.approved`
and `determinism.md` were each required by the routine and absent from the
acquisition step. Reviewers caught all three; a reviewer who misses it once


`digest_apply.py` WRITES and its check is already covered by `lesson_gate.py
audit`. `skill_lessons_backlink.py` WRITES to the lessons file, so it is on the
same footing - the nightly run may detect a missing pointer but never place one.
The selftests and `manifest_check.py` are deployment-time tools that a nightly
run never executes. Each is a decision, not an omission - which is the whole
point of naming them.

`skill_lessons.py` IS acquired, and only ever with `--check`. It writes nothing
in that mode and exits 1 when a skill's generated block no longer matches the
lessons file - the same staleness signal `lesson_gate audit` gives for the
digest, one tier down. Acquire `skill_lesson_routes.json` beside it: without the
routes the script cannot run, and a missing route file is the same class of
omission as the three that shipped on 2026-08-30.

`plugin_lessons.py` is the same contract one surface across, and is likewise
only ever run with `--check`. It covers what each PLUGIN TOOL carries in its
description rather than what each skill carries in its SKILL.md. Its routes
file is required for the same reason.

The two are not interchangeable and the difference is a budget, not a style.
A skill block costs context only when that skill loads; a tool description is
in context for every session where the plugin is connected. So a drifted
plugin segment is worth reporting even when no skill drifted, and an oversized
one is a finding in its own right - `plugin_lessons.py` prints each segment's
byte cost against its declared `max_bytes` on every run.

Only servers Jordan owns can carry a segment: 8933 (`batch-exec-server.js`) and
8934 (`flow-mcp-server.js`). 8931 and 8932 launch from `npx`, so an edit lands
in `node_modules` and is overwritten on the next start - their rules stay in
the companion skills, which `skill_lesson_routes.json` already covers. A route
naming an npx-launched server is a defect in the routes file, not a finding.

**When you add a rule that reads a file, add the file to `acquires:` in the same
edit.** Then run:

```bash
python manifest_check.py <skill>/SKILL.md --extra <skill>/references/determinism.md
```

## THE HARD RULE

**Propose. Never mutate the knowledge base.**

Stated as a boundary rather than a count, because the routine does take more
than one action and pretending otherwise invites an agent to resolve the
contradiction its own way:

- It MAY write one dated report under `Documents/Cowork/dream-reports/`.
- It MAY send one notification email referencing that report.
- In a LATER approved session it MAY append disposition metadata to a report
  (which proposals were applied, which declined).
- It MUST NOT edit, merge, reorder, retire or delete a lesson entry, a memory
  file, a built-in memory, `copilot-instructions.md`, the digest, the memory
  index, or any script.

The email counts as an action. So does the disposition update. Only the last
bullet is the actual prohibition.

The reason is not caution for its own sake. At 2am there is no one to ask, and
"superseded" is a judgement, not a measurement. A wrong retirement removes the
only record of a mistake and the mistake comes back. The entry
`artifact-deletion-reverts-after-verified-absent` also shows a deletion is not
always as final as it reads. So: the sweep finds, Jordan disposes.

If a run ever reports that it changed a lesson or memory file, treat that as a
defect in this skill and stop scheduling it.

## Run it when there is something to consolidate

A consolidation pass over an unchanged knowledge base produces yesterday's
report again, which trains the reader to ignore it - and Jordan is
cost-conscious about credit use, so a no-op sweep is a real waste.

**Compare a CORPUS CHECKPOINT, not the lessons file's date.** A built-in memory
can change, a pointer can break, or a proposal can be declined while
`cowork-lessons.md` sits untouched - and a date-only gate would stop and report
NO-OP over a corpus that had moved. The checkpoint covers lessons,
instructions, the memory index, the cowork-memory tree, built-in memory, the
digest block, proposal dispositions, and (FULL only) git HEAD. Exact hashing
and normalisation rules: `references/determinism.md` §1.

If every component matches the newest verified report, the run is `COMPLETE`
with Outcome `NO-OP`: write the minimal report, verify it, send the
notification. If any component differs, run the full analysis - even if the
findings look like yesterday's.

Note that built-in memory must be fully enumerated before its signature can be
computed, so the pagination requirement applies here too. That is the minimum
work needed to answer "did anything change" honestly, not overhead.

## Capability preflight - prove the surfaces, do not assume them

FULL mode is proven by calling a bridge. CLOUD mode had no equivalent check
until 2026-08-30, when a real test found the documented file-read call was
wrong - it needs `drive_id` + `item_id`, not a path, and the run would have
failed at step 1. Tool names and schemas differ by session and registration, so
resolve each surface with one harmless read-only call before writing anything:

| Surface | Proof |
|---|---|
| list files | `GetDriveChildren` on the memory folder returns entries |
| read a file | `ReadFileContent` on the lessons file returns bytes |
| file metadata / URL | `GetDriveItem` returns a URL |
| built-in memory | `list_memories` returns a page |
| write a file | see below - it cannot be preflighted |
| send email (CLOUD) | resolve the send tool before promising a notification |
| command bridge (FULL) | one live bridge call |

If a required surface is missing, STOP before writing a report and name the
surface. A report written without the memory surface is not a sweep with a gap;
it is a different, smaller thing wearing the same name.

**The write surface is the one thing that cannot be proven in advance** - you
cannot know a write will fail until you try it. So it is handled as a
post-condition instead: write the report, then READ IT BACK and confirm the
content and the byte count. If the write or the read-back fails, the run is
`INCOMPLETE`, and **no notification may claim a report exists**. Never send a
summary email whose report link points at a file you did not verify.

## Run states - say which one, every time

Ambiguity between "a section was omitted by design" and "a section failed" is
how a partial sweep gets read as a full one. Every run ends in exactly one:

| State | Meaning | Proposals? |
|---|---|---|
| `COMPLETE` | every input for the mode was read and validated | yes |
| `COMPLETE (expected limits)` | all CLOUD inputs read; git unavailable by design | yes |
| `INCOMPLETE` | a required input could not be retrieved OR memory pagination could not be exhausted OR the report write could not be verified | **no** |
| `FAILED INTEGRITY` | inputs retrieved but a required integrity gate failed: `lesson_check` failure, digest audit failure, missing or malformed `analyser.approved`, or an analyser hash mismatch | **no**, report the failure only |

A stale per-skill block (`skill_lessons.py --check` exit 1) is deliberately NOT
`FAILED INTEGRITY`. Staleness there means a lesson was edited and a generated
copy has not caught up - the data is sound and the proposals derived from it are
still valid. It is reported as a finding with the affected skills named. Exit 2
is different: the script could not run, which IS `FAILED INTEGRITY`, on the same
reasoning that makes an unwritable receipt directory exit 2 rather than 1.

Only the first two may carry proposals. `INCOMPLETE` and `FAILED INTEGRITY`
report what broke and stop - a proposal derived from data that failed
validation is worse than no proposal.

A failed run may still write a DIAGNOSTIC report and send a failure
notification. The distinction is absolute: a **diagnostic observation** explains
what broke; a **proposal** recommends a change to the knowledge base. A run that
is not `COMPLETE` may produce the first and never the second.

Separately, `Outcome` describes the findings, not the data quality. A run can be
perfectly `COMPLETE` and find nothing:

| Outcome | Meaning |
|---|---|
| `PROPOSALS` | at least one actionable proposal |
| `NO-OP` | corpus read cleanly, nothing changed since the last report, or nothing found |
| `FAILED` | see the State line |

State is about the data. Outcome is about the findings. Report both, always.

## Proposal identity - stable IDs, not positions

"Apply 3" is ambiguous the moment a report is regenerated or reordered. Every
proposal gets an ID that survives a rerun:

```
DC-<date>-<TYPE>-<nnn>      e.g. DC-2026-08-31-MERGE-001
```

Types: `MERGE`, `RETIRE`, `DATE`, `MEMORY`, `RULE`, `POINTER`.

Each proposal in the report carries: `id`, `type`, `target` (the key or file),
`evidence`, `measured_or_judged`, `proposed_change`, `status`.

`status` starts `proposed` and becomes `applied` or `declined` in a later
approved session.

**The ID identifies the instance; a FINGERPRINT identifies the substance.**
Because an ID carries the run date, the same declined proposal detected again
tomorrow arrives with a new ID and slips straight past ID-based suppression. So
every proposal also carries a fingerprint over its type, sorted normalised
targets, and operation - canonical serialisation and hashing in
`references/determinism.md` §2, because "normalised" without a defined
procedure lets punctuation or ordering split one proposal into two.

**Do not re-propose a declined FINGERPRINT.** Reopening one requires linking
the prior ID and stating the new evidence and the substantive difference (§2).
Silently re-raising a declined proposal under a fresh ID is how a nightly
report becomes something Jordan stops reading.

## Routine

1. **State the mode** in one line before anything else.

   raise the ceiling. Both are exit 2. Say which one, and say that nothing was
   written.

   This opens ONE server file per route - currently two, 8933 and 8934. It
   reads no `node_modules` and never scans the Startup tree.
3. **The day's work** - FULL mode only. What was committed, what changed.
4. **Relative dates.** The analyser flags anchors like "today" or "yesterday"
   that are unrecoverable once the session ends, and names the entry's own
   `Date:` field as the resolution. Propose the exact replacement text; never
   apply it. Note that `now`, `earlier` and `this session` are deliberately NOT
   flagged - on this corpus a broad pattern hit 43 times and only 3 were real.
5. **Built-in memory review** - `list_memories`. Look for: a memory that
   contradicts a lesson, a memory describing a file or script that has since
   changed, a `ptr-` pointer whose deep file no longer exists, and near-duplicate
   keys. Report the key and the conflict; propose no deletions beyond naming them.

   **Exhaust the pagination.** `list_memories` returns a page, not necessarily
   the whole store. On 2026-08-30 it returned 50 of 81 and all four
   contradictions came from that half - which says nothing about the other 31.
   Continue until every page is retrieved, then deduplicate by key.

   **If pagination cannot be exhausted the run is `INCOMPLETE`.** Record how
   many were retrieved, generate NO proposals from ANY section, and go straight
   to the diagnostic-report path. There is no PARTIAL-but-carry-on option: the
   memory store is a required surface, and a sweep over a smaller corpus is a
   different thing wearing the same name. Make no claim about absence,
   uniqueness, duplicate counts or total conflicts from a partial store - "no
   duplicates found" over 50 of 81 is a false statement dressed as a
   measurement.
6. **Write the report** to `Documents/Cowork/dream-reports/YYYY-MM-DD.md`.
7. **Report in chat** in the short format below.

## Getting the report to Jordan, and the morning handoff

The 2am run happens in its OWN conversation. Nothing carries it into the chat
Jordan opens the next morning - a fresh session has no idea the sweep ran, and
the report will sit in OneDrive unread unless something pushes it.

**So the CLOUD run emails it.** After writing the report, send Jordan the short
summary block plus the proposal headings, subject `Dream cycle - <date> - N
proposals`. It lands in his inbox overnight and is there when he starts. If the
run found nothing worth acting on, say that in one line and still send it - an
absent email is indistinguishable from a failed run.

**Link to the REPORT, never to a chat.** Use ONLY the exact URL returned by
`GetDriveItem` after the write is verified. Never infer or reconstruct it from
the path, the tenant, the user name, or a previous report - a plausible URL that
404s is worse than no link, and a remembered URL shape is exactly the kind of
stale detail that decays silently. If the metadata call does not return a URL,
send the email naming the report's folder and filename in plain text and say the
link was unavailable.

Do NOT promise a link back to the 2am conversation, and do not link to one even
if a URL is available. That session ran while the PC was asleep, so it had NO
bridges - and the tool surface is fixed at session start, which means that
conversation can never apply a proposal no matter when it is reopened. Sending
Jordan there would be sending him to a dead end that looks like the right
place. The email should say plainly: read this, then start a NEW chat at your
PC and say "dream".

**Write the email so the decisions can be made from the email itself.** Jordan
should be able to read it on a phone over coffee and arrive at his desk knowing
what he wants to approve. List the proposals one line each with the key or file
they touch, and show BOTH a short ordinal for readability and the stable ID.

Approvals reference the **ID**, never the ordinal:

```
1. DC-2026-08-31-MERGE-001  merge bridge-x into bridge-y (both 1 hit)
2. DC-2026-08-31-DATE-003   "today" in onedrive-user-surface-not-live -> 2026-08-18
3. DC-2026-08-31-MEMORY-002 fact-expansion-items... claims no .git; repo exists
```

He replies "apply DC-2026-08-31-MERGE-001 and -DATE-003, decline -MEMORY-002".
The ordinal is a reading aid; the ID is the instruction. Never accept an
approval that names only ordinals - reports get regenerated and reordered, and
"apply 3" would then point somewhere else.

Keep the body short. The report holds the evidence; the email holds the choices.

**The morning half is NOT scheduled and must not pretend to be.** Applying the
proposals needs the bridges, so it happens when Jordan is at his PC and asks.
When he opens a session and says "apply the dream proposals", "what did the
dream find", or just "dream":

1. Read the newest file in `dream-reports/` - do not re-run the sweep first.
   Check its `State` line. If it is `COMPLETE` or `COMPLETE (expected limits)`
   and holds unresolved proposals, work from it. Otherwise report that run's
   state plainly, then search BACKWARD for the newest report that does have
   actionable proposals - and say clearly that the report you are working from
   is not the latest run. A recent failure must never be skipped silently just
   because an older report is more useful.
2. Prove the bridges by CALLING one. If they are not there, say so and stop;
   the proposals cannot be applied from the cloud side.
3. Approval covers one or more INDIVIDUALLY IDENTIFIED proposals. "Apply
   DC-2026-08-31-MERGE-001 and -DATE-003" is valid; "apply all the merges" or
   "apply everything" is NOT - a category is not an identification. Before
   executing, restate the exact proposal IDs, the files or keys each touches,
   and the change each makes, as ONE bounded change set, and let Jordan correct
   it before anything runs.

   This matches his established command-bridge workflow - one explicit approval
   of a fully specified batch - rather than inventing a stricter rule here that
   the email format then contradicts.
4. Apply through the OWNING skill, then run the normal close: `lesson_check`
   bare, `digest_apply`, `lesson_gate audit`, commit via `cowork-close.bat`.
5. Note in the report file which proposals were applied and which were
   declined, so the next sweep does not re-propose a declined one.

If Jordan never asks, nothing happens - and that is the correct behaviour, not
a gap to engineer around. An unattended agent applying yesterday's proposals to
a knowledge base is the exact failure this skill exists to avoid.

## Fencing the judged half

These exist because an unattended agent with no ground truth will otherwise
produce confident, plausible, wrong analysis.

- **Never claim a better path existed without naming it and its evidence.**
  "The apportionment step could have been faster" is noise. "Commit 3f9a ran the
  schema probe after writing the conversion; `alteryx-skip-schema-check-costs-a-run-cycle`
  says run it first" is a finding. If there is no specific alternative, say the
  day looked unremarkable. **An unremarkable day is a valid result.**
- **Separate MEASURED from JUDGED** in the report. Every mechanical finding
  carries its number. Every judged one names the entry or commit it rests on.
- **Never propose retiring an entry you have not read in full.** The mechanical
  flag is a pointer to read it, not a verdict.
- **Do not invent a Pattern-Key.** A key that reads as a citation and resolves to
  nothing is the same failure as a hand-transcribed lookup table. Check every key
  you name against the file.
- **Contradiction beats recency.** If a memory and a lesson disagree, report both
  and say which is better evidenced - do not assume the newer one is right.
- **Say when a section could not run.** No git in CLOUD mode is a gap to state,
  not a section to drop.

## Output format

```
Dream cycle - <CLOUD|FULL> - <date>
State:     <COMPLETE | COMPLETE (expected limits) | INCOMPLETE | FAILED INTEGRITY>
Outcome:   <PROPOSALS | NO-OP | FAILED>
Integrity: lesson_check <exit> | <N FAIL, N WARN> | digest <N rules / M entries>
Skill blocks:  <CURRENT | STALE> - <N> of <N> skills, <N> routed entries
Plugin blocks: <CURRENT | STALE | REFUSED> - <N> tools, <N> rules, <N>% of budget
Reach:     <N>% of entries reach a session | weakest surface: <name> <N>%
Memory:    <N of N enumerated>
Proposals: <N merge> <N retire> <N relative-date> <N memory conflict>
Day:       <commits reviewed, or "git unavailable in CLOUD mode">
Report:    dream-reports/<date>.md
Nothing was changed.
```

On a failure state, do NOT pad the success fields with invented values. Use:

```
Dream cycle - <CLOUD|FULL> - <date>
State:     <INCOMPLETE | FAILED INTEGRITY>
Outcome:   FAILED
Failure:   <the surface, input, or integrity gate that failed>
Completed: <the stages that did validate>
Proposals: none generated
Report:    <path, only if a diagnostic report was written AND verified>
Knowledge base unchanged.
```

**A failed NOTIFICATION is not a failed run.** If the report was written and
read back successfully and only the email send failed, the State and Outcome
stand as they were - the analysis is complete and preserved. Report the delivery
failure separately as `Notification: FAILED - <reason>`. Downgrading a valid,
verified analysis to `INCOMPLETE` because a mail call failed would discard good
work and misdescribe what actually happened. The reverse still holds absolutely:
a notification may never claim a report that was not verified.

Keep the chat summary to that. The detail belongs in the report, which Jordan
reads when he wants it.

## When NOT to Use

- Logging a single lesson from the session just finished -> `self-improvement`.
- Saving or updating one memory -> `persistent-memory`.
- The session open/close bookend -> `gamma-tango`.
- A plain git question -> `git-bridge`.
- Applying the proposals. That is a normal approved session with the owning
  skills, not another dream run.

## Guardrails

- **Read-only is the whole safety model.** `dream_analyze.py` is proven
  read-only by `dream_analyze_selftest.py`, whose first cases hash the protected
  tree before and after a full run. The deployment gate requires the COMPLETE
  CURRENT SUITE to pass - not a fixed number of cases, which goes stale the
  moment a test is added. On a pass it writes `analyser.approved`; on a failure
  it removes the marker and scheduling must stop.
- **A finding is not a fact.** The mechanical pass reports pattern matches. It
  flagged 40 of 87 entries on its first run because a case-insensitive match read
  the ordinary word "wrong" as the marker WRONG. Every detector needs a negative
  control before its output is believed.
- **Never let the report grow into a second lessons file.** It is a work list
  with a date on it, not a place to restate a lesson's mechanism.
- **Reports are not free to delete.** They carry the disposition history that
  stops a declined proposal being raised again every night. A report is
  immutable except for its `status` fields. Keep them; if the folder ever needs
  pruning, that is an approved maintenance task that first preserves the IDs and
  dispositions into a compact ledger - and it is never done by the dream cycle
  itself.
- **No autonomous cleanup, ever, in any mode** - including when Jordan has
  previously approved a similar-looking proposal. Approval attaches to specific
  proposal IDs, never to a category or a resemblance. "He approved a merge like
  this last week" authorises nothing.
- **This skill does not create or manage its own schedule.** The 2am run exists
  because a scheduled Copilot prompt invokes it; the skill only defines what to
  do once invoked. Do not read the trigger phrase in the description as evidence
  that a schedule exists - check `GetScheduledPrompts` if it matters. If the
  invocation arrives without the M365 file, memory, or email surfaces the
  preflight requires, stop and name the missing surface rather than improvising
  a reduced sweep.
- **If the knowledge base cannot be read, stop and say so.** Do not produce a
  report from partial data that reads as a full sweep.
