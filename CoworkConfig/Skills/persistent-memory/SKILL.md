## What this does

- **Loads** the right memory file(s) when work on a focus area begins.
- **Saves / updates** a structured memory file when a session concludes.
- Keeps everything in the user's **`Documents/Cowork/cowork-memory/`** folder (visible
  and editable by the user), indexed by a small `MEMORY-INDEX.md` for fast lookup.
- **One file per distinct topic** — and at the end of a chat it consolidates a newly
  created file into an existing one when they cover the same thing, so topics don't fragment.

## When NOT to Use

- A single self-contained question where prior context adds nothing — answer inline.
- Requests to store raw transcripts, credentials, or full confidential documents.
- Note-taking that another active skill already owns for its own workflow.
- Another skill's wrap-up phrasing that is not about *this* conversation — e.g. "wrap up my
  day" is the daily briefing, not a memory save. Only act on end-of-conversation signals for
  the current topic; defer to the skill that owns the request.

## Where memory lives

| File | Path (in OneDrive) | Role |
|------|--------------------|------|
| Index | `Documents/Cowork/cowork-memory/MEMORY-INDEX.md` | One row per focus area — read this FIRST |
| Memory file | `Documents/Cowork/cowork-memory/<focus-slug>.md` | The structured memory for one focus area |

- `<focus-slug>` is a stable **kebab-case** name (e.g. `q3-tax-provision`, `client-acme-etr`).
  The same slug is the filename AND the index key — this is what makes matching reliable.
- **Write path (revised 2026-08-24):** write the file on the PC through the 8932 filesystem
  bridge at `C:\Users\YOURUSER\OneDrive\Documents\Cowork\cowork-memory\<slug>.md`.
  The repo sync sees it in the same session, and OneDrive carries it upward afterwards.
  The older route — `output/cowork-memory/…` via CreateArtifact / EditArtifact (surface
  `output`) — still lands at `Documents/Cowork/cowork-memory/`, but CLOUD-side: the desktop
  client may take tens of minutes to pull it down, so use it only when the bridge is down.
- **Read path (a fresh session starts with an empty workspace):** fetch from OneDrive —
  `GetDefaultDrive` → `SearchDrive`/`GetDriveChildren` → `ReadFileContent`.

## Operation A — Determine focus, then load or create (during the chat)

**Monitor the conversation until the main focus is clear — do not act on a vague opener.**
On each early turn, judge whether the topic is now unambiguous. It usually resolves on the
first substantive request, but if the opening is chatty or exploratory, keep watching and
act the moment it does. Run this once per chat — once a topic is loaded or created, stop
re-running it.

1. **Get the drive:** `GetDefaultDrive` (no site_id) → the user's OneDrive `drive_id`.
2. **Read the index first — use the deterministic folder path.** Navigate to the
   `cowork-memory` folder and `GetDriveChildren` it, then `ReadFileContent` the
   `MEMORY-INDEX.md`. Prefer this over `SearchDrive(query="MEMORY-INDEX")`, which returns
   noisy keyword hits — fall back to search only if the folder path does not resolve.
   - If no index/folder exists, this is the first-ever run — go straight to step 4.
3. **Match** the current focus to an index row by slug **and** keywords/synonyms (a chat
   about "the Q3 footnote" matches `q3-tax-provision`). If one (at most two) files are
   genuinely relevant, `ReadFileContent` them — never bulk-read the folder — ground the
   session, and say one line: "Loaded what we captured on `<focus>` (updated `<date>`)."
4. **No relevant file? Create one now.** Mint a stable kebab-case slug, seed a file from the
   template (title, slug, created date, a one-line summary, and any facts already
   established), write it to `output/cowork-memory/<slug>.md`, and add its index row. Say:
   "New topic — I've started a memory file for `<focus>`." Creating it now, not just at the
   end, means the topic is captured even if the chat ends abruptly.

## Recognizing the end of a session

Run the final memory procedures (**Operation B**) when any of these appear. The first four
are visible in the conversation and are the reliable triggers; the fifth is a known blind
spot — read its note.

1. **Objective met / final artifact delivered.** The user uploads a file or screenshot of
   the finished product, or points to a final result, and you can confirm the goal is
   complete. Confirm completion, then run Operation B.
2. **Refinement has converged.** Across several turns the edits have shrunk to minor tweaks —
   the product is essentially done. Treat that convergence as an end signal and checkpoint
   now; do not wait for a silent pause (this skill cannot see one).
3. **The conversation structurally concludes.** A sign-off or thanks, "that's what I needed",
   a wrap-up with no follow-up, or the run of requests is fully resolved. Run Operation B.
4. **The user indicates they are done.** Any "I'm done / that's all / wrap up / finished."
   Run Operation B.
5. **Extended pause between prompts.** **This skill cannot detect elapsed time by itself** —
   the agent only runs when a message arrives, so a silent gap (or the user simply closing the
   chat) triggers nothing. Handle it two ways:
   - **Checkpoint early.** The moment signals 1–3 make the work look finished, run Operation B
     right away — capturing memory before the user steps away beats a save that never fires.
   - **Catch up on return.** If a message arrives that clearly resumes after a long gap, run
     Operation B for the earlier stretch first, then continue.

Saving is safe to repeat: Operation B merges into the same topic file without duplicating, so
an early checkpoint plus a later "done" simply refreshes it. When in doubt, checkpoint.

## Operation B — Conclude: update, then consolidate (session end)

Run this when a session-end signal fires — see **Recognizing the end of a session** above.
It is safe to run more than once (checkpoint early, then refresh at the true end).

1. **Distill the session — do not paste raw chat.** Extract into the schema sections below
   (facts, decisions, open threads, preferences, key exchanges as short dated points).
   Convert relative dates ("last Tuesday") to absolute dates.
2. **Write into this chat's topic file** — the one loaded in Operation A step 3 or created
   in step 4. Merge, don't duplicate: append new facts/decisions, refresh "Last Updated",
   move resolved items out of "Open Threads". Refresh its index row.
3. **Consolidation check — only when a NEW file was created this chat.** Re-read the index
   and compare the new topic against every existing topic: the focus may have sharpened
   during the chat, or a sibling file may exist under a slightly different name. If the new
   topic clearly belongs with an existing one:
   - **Merge** the new content into the existing file (append distinct facts, decisions, and
     open threads — no duplicates) and refresh its "Last Updated".
   - **Retire the redundant file:** remove its index row and replace its body with a one-line
     tombstone — `# Merged into <target-slug> on <YYYY-MM-DD>`. Use a tombstone, not a hard
     delete: OneDrive files can't be reliably deleted through the available tools, so
     blanking + de-indexing is the robust way to retire a file.
   - Say: "This overlapped `<existing focus>`, so I merged it in."
   If the new topic is genuinely distinct, leave it as its own file — that is the intended
   one-file-per-topic result.
4. **Confirm the write landed.** Bridge path — re-read the file or `get_file_info` it and
   confirm size and modified time changed. `output/` fallback — `Glob output/cowork-memory/**`.
   Then tell the user it saved to their Documents/Cowork/cowork-memory folder.

## Operation C — Export / package memory for sharing

Triggered when the user asks to zip, export, or package memory to hand off (e.g. into a
Copilot chat). Because the point is to share *current* context, always checkpoint first so
the bundle is never stale.

1. **Checkpoint the current conversation FIRST.** Run Operation B (distill → merge) on this
   conversation's topic file so facts up to this moment are captured. Saves are idempotent, so
   this is safe even if you already saved earlier in the chat. Skip only if nothing new has
   happened since the last save.
2. **Select the files to include.** For "this conversation," that is the current topic file.
   For a stated topic, read `MEMORY-INDEX.md` and match by slug + keywords, then take the
   relevant file(s) — do not include the whole folder unless the user asks for everything.
3. **Gather from OneDrive.** `ReadFileContent` each selected file from
   `Documents/Cowork/cowork-memory` (a fresh workspace starts empty) and write copies into a
   scratch folder under `working/`.
4. **Confidentiality check before it leaves.** Confirm the selected files carry no
   client-confidential detail (the storage guardrail keeps them clean, but sharing sends them
   outside the user's control, so verify).
5. **Zip and deliver.** Create one archive of the selected files and place it in the output
   folder (e.g. `output/memory-export-<topic-or-date>.zip`). Confirm with `Glob output/**`
   before telling the user, and name what is inside.
6. **Say what was included**, making clear it is current — e.g. "Packaged the up-to-date
   `<topic>` memory (checkpointed just now) into memory-export-`<topic>`.zip."

## Memory file schema (template)

Every memory file uses exactly this structure so future sessions can parse it fast:

```markdown
# Memory: <Focus Area Title>

- **Slug:** <focus-slug>
- **Created:** <YYYY-MM-DD>
- **Last Updated:** <YYYY-MM-DD>
- **Sessions captured:** <n>

## Summary
<2-3 lines: what this focus area is and where it currently stands.>

## Key Facts
- <Durable fact the next session needs. One per line.>

## Decisions Made
- <YYYY-MM-DD> — <decision> — <why>

## Open Threads / Next Steps
- [ ] <Unfinished item or the agreed next action.>

## Preferences & Constraints
- <How the user wants this work done: format, tone, tools, do's/don'ts.>

## Key Exchanges
- <YYYY-MM-DD> — <distilled instruction or important Q&A — NOT a raw transcript.>

## Reference Links & Files
- <File name, report name, or link the work depends on.>
```

## Index file format

```markdown
# Cowork Memory Index

| Slug | Focus Area | Hook | Last Updated |
|------|-----------|------|--------------|
| q3-tax-provision | Q3 Tax Provision | Footnote + JE rollforward workflow | 2026-07-21 |
```

Keep the hook to one short line — it's what a future session scans to pick the right file.

## Performance — lazy, non-blocking load

The memory load is **deferred**, never run at session open — so it cannot slow down the
start of a chat:

- **Nothing happens at startup.** The skill's instructions are not in context until it is
  invoked, and the memory fetch waits for the user's first real message. Opening a chat and
  typing is never blocked.
- **Load on the first substantive turn only**, folded into answering that request — so the
  OneDrive fetch overlaps with work already underway instead of adding a separate wait.
- **Index-first, one file.** Read the small `MEMORY-INDEX.md`, match, then fetch the single
  relevant memory file. Never bulk-read the folder.
- **Skip entirely for trivial first turns** (greetings, quick one-off questions) — don't pay
  the fetch when there is nothing to ground.
- Deferral keeps startup instant. The only way to remove the OneDrive fetch from the first
  response as well is a fast local cache of the memory files — not used here because the user
  chose a single visible copy in Documents/Cowork.

## Efficiency & size limits

- **One focus area per file.** Do not let a file become a catch-all.
- **Distilled, not verbatim.** Short bullet points beat pasted conversation — they load
  faster and avoid storing sensitive text.
- **Prune as you go.** When an open thread closes, move it to Decisions or delete it.
  Keep each file to roughly the most relevant ~1-2 pages.
- **Absolute dates only** so age is unambiguous across sessions.

## Honest limitations (state these; don't hide them)

- **Auto-load at session start** needs a one-line entry in the user's personal
  instructions (`copilot-instructions.md`) telling every new session to consult this
  skill. Without it, the user loads memory by asking ("load my memory") or by starting
  work on a known focus area.
- **A true 30-minute idle auto-save is not possible** — the agent is not running while
  the user is away, so nothing can detect the timeout and write. Reliable save happens
  when the user says they're done, or when a session visibly wraps. If a prior session
  ended without saving, the next session reconstructs what it can and flags the gap.
- **Sync latency:** saved files appear in OneDrive / the PC's Documents folder within
  ~35 seconds.

## Failure handling & edge cases

- **Memory read fails or is empty** → proceed with the task without memory, say so in one
  line ("couldn't reach saved memory this time"), retry the fetch once; never block the
  user's work on it.
- **Write or sync fails** → do not claim a save succeeded. The delivery-gate `Glob` is the
  check; if the file is not there, retry the write once, then tell the user plainly.
- **Concurrent chats, same topic** → before writing, re-read the current file from OneDrive
  and merge into that latest version, so a parallel conversation's edits are not overwritten.
- **Slug collision** → if a freshly minted slug already names a *different* topic, add a short
  qualifier (e.g. `client-acme-etr-2026`) so two topics never share a file by accident.
- **Tombstones are inert** → a retired file is ignored on load because the index no longer
  points to it; leave it in place.
- **Index stays small** — one row per topic. If it ever grows unwieldy, that is the cue to
  consolidate near-duplicate topics, not to bulk-read files.

## Guardrails

- Never store raw transcripts, passwords, secrets, or client-confidential detail — named
  clients tied to figures, PII, or privileged tax/financial specifics. Keep only the minimum
  needed to resume: the topic, decisions, preferences, open threads, and pointers to files.
- Never hard-delete a user's files. This skill only creates, edits, and merges; a superseded
  file is retired by blanking it to a one-line tombstone and de-indexing it — nothing is
  removed from the user's OneDrive.
- Never fabricate — record only what actually happened in the session.
- Always read the index first; never bulk-read the whole memory folder.
- Keep the index in sync with the files on every save.
- Confirm the write actually landed before telling the user a save succeeded — by re-reading
  the file when written through the bridge, or with `Glob output/cowork-memory/**` when the
  `output/` fallback was used.
- On export/sharing: checkpoint the current conversation first so the shared bundle is never
  stale, and verify the selected files carry no client-confidential detail before they leave
  the user's control.
