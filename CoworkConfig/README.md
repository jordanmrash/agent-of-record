# CoworkConfig

This folder mirrors what the author's Microsoft 365 Copilot Cowork loads from
his OneDrive `Documents\Cowork` folder, as of the release it ships in. It is the
configuration half of the repository: the bridges under `Startup/` give an agent
reach, and these files give it rules, history and a place to write.

Nothing here is loaded from the repository. Cowork reads the OneDrive folder;
the repository holds a copy so the corpus is versioned, gated and published.
[`docs/setup.md`](../docs/setup.md) step 11 copies it into place.

## What is here

| Path | Installs to (under `Documents\Cowork`) | What it is |
|---|---|---|
| `Skills/<name>/SKILL.md` | `skills\<name>\SKILL.md` | Ten skills. Each has a frontmatter block Cowork reads at session start and a body it loads when the skill fires. |
| `Skills/self-improvement/scripts/` | with its skill | The lesson tooling - `lesson_check`, `lesson_dupe`, `lesson_gate`, `digest_apply`, `skill_lessons`, `plugin_lessons`, `scope_check`, `job_lint`, `verify_delivery`, `dream_analyze`, `nightly_measure` - and the ten negative-control self-test suites the release gate runs against them. |
| `Skills/_ATTRIBUTION-TEMPLATE.md` | - | The attribution block every skill carries. |
| `copilot-instructions.md` | `copilot-instructions.md` | Standing instructions, including the generated lesson digest. |
| `cowork-memory/cowork-lessons.md` | `cowork-memory\cowork-lessons.md` | The lessons corpus: dated entries keyed by `Pattern-Key`, each with a Failure, a Why, a Worked-instead and an evidence tag. |
| `cowork-memory/MEMORY-INDEX.md` | `cowork-memory\MEMORY-INDEX.md` | One row per memory file; read it first. |
| `cowork-memory/<topic>.md` | `cowork-memory\<topic>.md` | One memory file per focus area; the schema is the one the existing files use. |
| `cowork-memory/verification-ledger.json` | `cowork-memory\verification-ledger.json` | Verdicts from `verify_delivery.py`: which delivered rules were judged effective, against which control, keyed by a fingerprint of the text that was judged. |

## What is generated from what

Three kinds of block are written by scripts and audited by the release gate.
Editing them by hand is undone at the next regeneration and fails the `--check`
that guards each one.

| Block | Lives in | Generated by | From |
|---|---|---|---|
| `<!-- LESSON-DIGEST:BEGIN … END -->` | `copilot-instructions.md` | `digest_apply.py` | rules in `cowork-lessons.md` |
| `<!-- SKILL-LESSONS:start … end -->` | each `SKILL.md` | `skill_lessons.py` | rules routed to that skill by `skill_lesson_routes.json` |
| `/* PLUGIN-LESSONS:start … end */` | `Startup/CommandBridge/batch-exec-server.js`, `Startup/FlowBridge/flow-mcp-server.js` | `plugin_lessons.py` | rules routed to that server by `plugin_lesson_routes.json` |

The corpus is the source; the blocks are delivery. A rule that is in the corpus
but reaches no skill and no server is delivered nowhere, and the gate's surface
audit says so. Fix a rule by editing its entry in `cowork-lessons.md` and
regenerating - never by editing the block.

The self-improvement skill's `SKILL.md` documents the entry format and the
close-of-session gate. `lesson_gate.py preflight` refuses a missing or stale
digest and a digest whose body was edited without regenerating, and flags a
repeatedly hit lesson that still has no Rule line; `lesson_dupe.py` refuses a
near-duplicate entry; `lesson_check.py` refuses an entry with no evidence tag.

## Starting with an empty corpus

The shipped `cowork-lessons.md` (123 entries), the two memory files and the
ledger are one operator's record. They cite his machine, his measurements and
his decisions, with dates. Read them to see what a corpus looks like after
weeks of daily use; do not operate under them, because an agent that loads
another operator's lessons will act on failures you never had.

To begin empty, in your installed `Documents\Cowork\cowork-memory` folder:

1. **Set the shipped corpus aside** - rename `cowork-lessons.md` to
   `cowork-lessons.reference.md`, or delete it. Do the same with the two topic
   files and `verification-ledger.json`.
2. **Create an empty `cowork-lessons.md`.** Keep the header from the shipped
   file - everything above the first `## Failures` line - because it documents
   the entry format and the evidence key. Below it, the three sections, empty:

   ```markdown
   ## Failures

   ## Contradictions — stored memories that proved wrong

   ## Open questions
   ```

3. **Create an empty `MEMORY-INDEX.md`** with the shipped file's title and
   table header and no rows. Add a row when you
   starts a topic file.
4. **Regenerate the delivery blocks** so no rule from the reference corpus
   remains in your instructions or skills. From the repository root, with
   `$cm` pointing at your `cowork-memory` folder and `$sk` at your `skills`
   folder:

   ```powershell
   $tools = "CoworkConfig\Skills\self-improvement\scripts"
   python "$tools\digest_apply.py"  --lessons "$cm\cowork-lessons.md" --instructions "$cowork\copilot-instructions.md"
   python "$tools\skill_lessons.py" --lessons "$cm\cowork-lessons.md" --skills-dir $sk --routes "$tools\skill_lesson_routes.json"
   python "$tools\plugin_lessons.py" --lessons "$cm\cowork-lessons.md" --servers-dir Startup --routes "$tools\plugin_lesson_routes.json"
   ```

   Each reports zero rules routed and rewrites its blocks accordingly. A skill's
   block keeps its heading and reads `0 rule(s) of 0 entries routed to this
   skill`, which is the correct state for a corpus with nothing to deliver.

Two things to expect. `lesson_check.py` reports `FAIL no_entries` on a file with
no `###` entries - deliberately, because an empty parse and an empty corpus look
the same to it, and it must not pass a broken parse. The first `gamma tango
close` that logs a lesson clears it. And `verification-ledger.json` is written
by `verify_delivery.py` when it is run with `--ledger`; nothing needs it to
exist before the first judgment.

## Keeping the copy and the live folder in step

The live folder is the one Cowork reads; this folder is a snapshot of it.
The author's `gamma-tango` close commits the live folder into a local
repository after every session, and `GitHubSetup/` sanitizes and publishes a
snapshot of that repository. If you version your own corpus, the same shape
works: live folder in OneDrive, git repository beside it, sanitizer between the
repository and anything public. `scripts/public_scan.py` is the sanitizer's
check and `GitHubSetup/PUBLISHING.md` is the procedure.
